Three steps, in this order

This is section 1 of the specification — the authoring protocol — in plain English. The model you prompt reads the same four steps in machine-readable form.

✍️

1. Describe your business — properly

Not one sentence. Write what you would tell a new hire on their first day: what you sell or service, every kind of record you keep, who touches each one, the states things move through, what needs approving and by whom, and what happens when a step fails.

The thinner the description, the thinner the application. This is the step that decides the result.

🔎

2. Hand it over to ChatGPT

Give the model our machine-readable specification along with your description. It carries the authoring protocol: enhance the brief into a full entity model, workflows and business rules; write the model file; then validate it against our published checker before handing anything over.

You get back a single .mmd file — the model itself, not a document describing it — plus the specification it inferred, so you can correct what it guessed.

▶️

3. Run it, here, in this browser

Upload that file and watch it become a complete application — PostgreSQL compiled to WebAssembly, a real API, a real interface, business rules and workflows running. No install. No signup. Nothing leaves your machine.

Your model is parsed in the tab, the app is assembled in the tab, and its database lives in the tab.

The prompt — copy it as it is

Replace only the description. Everything else tells the model where the specification lives and what it must do before it answers you. For a professional or enterprise application, use the same prompt against the detailed specification instead — same words, a longer conversation, a model nobody had to guess. Already have a .mmd? Both of these write a model from nothing; the enhancement prompts start from the file you already have and give it back whole.

Read https://www.appwithai.org/llms-full.txt in full, and follow section 1 — the authoring protocol — exactly.

My business:
[Describe it here. What you sell or service. Every kind of record you keep and how they relate. Who does what. The states each record moves through. What has to be approved, and by whom. What happens when a step fails.]

Deliver exactly one file I can download: <business-name>.mmd. It must open on a %% line with %%meta name: before the first diagram, and every line in it must be Mermaid or an EML %% directive — no Markdown, no headings, no prose. A document that describes the model is not the model; the checker scores that EML004.

Send no other file — no specification document, no report, no README. If you can only answer with a document, put the entire model in the first fenced mermaid block of that document, before any prose.

Then, in your reply text: the enhanced specification you inferred, the checker result with its counts, and anything you assumed. If the checker cannot be reached from where you are running, say which host failed and how, deliver the model anyway, and keep going — never invent counts, and never hold a phase open waiting for a network call.

Then bring the file back

Upload the .mmd and press Generate, then Run. The first time PostgreSQL loads it takes a few seconds; after that it is instant.

Got a report instead of a file? Some models can only answer with a document. Copy its mermaid block into the checker page, check it, and download a real .mmd from there.

For professional and enterprise software

Building something serious? Point the same prompt at the detailed specification

The prompt above is right for a first model — one pass, one answer, a file back in a couple of minutes. It is the wrong trade once the business is large enough that guessing it in a single pass is guessing. For that there is a second specification, llmdetailed.txt: the same language, the same diagnostics, the same checker — plus how the generator, the templates and the generated application actually work, and a different authoring protocol in its section 10.

What section 10 does differently

Section 1 of llms-full.txt is the batch protocol: read the brief, infer the model, write it, validate, deliver. Section 10 of llmdetailed.txt is the interactive one — seven phases separated by approval gates you have to pass before the model moves on.

  • Phase 1 — research your business, and show you what it found
  • Phase 2 — agree the entity roster before a line is written
  • Phase 3 — seed the .mmd, and build it on disk from here on
  • Phase 4 — walk the entities one at a time, checking after each
  • Phase 5 — the cross-cutting pass: processes, the access matrix, coverage
  • Phase 6 — validate to clean, and escalate what needs your decision
  • Phase 7 — deliver

It costs a conversation instead of a reply. What you get for it is that nothing about your business was inferred without your seeing it, and the help: text — the only help your users will ever get, and the whole of the manual the generator writes — is still written by entity fifteen.

Read https://www.appwithai.org/llmdetailed.txt in full, and follow section 10 — the interactive authoring protocol — exactly. Do not skip a phase, and do not cross a gate I have not approved.

For a model you already have

Load your file, describe the change, get the whole model back

There is a second pair of specifications for this, because enhancing is not authoring and the ways it goes wrong are its own. llmtextenhancement.txt is the one-pass form: the model reads your file, shows you what is in it, applies your change, and hands the file back whole. Its section 1 is the enhancement protocol.

What it does that the authoring prompt cannot

An authoring prompt pointed at an existing model rewrites it. A rewrite is a new model wearing the old one’s name — and what it loses, no checker reports.

  • It asks for your file first — and refuses to work from a summary or a description
  • It reads and counts your model before editing — entities, roles, reports, help text
  • It follows the change through the file — a new entity also needs access rules, help and enum bindings
  • It hands back the whole file — not a patch you have to merge yourself
  • It proves nothing was lost — the before-and-after counts, side by side

That last one is the point of the whole thing. A model that quietly came back with two fewer %%rbac lines and no help text on three entities passes the checker exactly like one that did not — so the count is the only thing that catches it.

Read https://www.appwithai.org/llmtextenhancement.txt in full, and follow section 1 — the enhancement protocol — exactly.

My model is attached. Do not start until you have read it, and do not rebuild it from anything else — not from a summary, not from this conversation, not from an earlier draft.

What I want changed:
[Describe it here. What to add, what to change, what to remove. Who does the new work. What states the new records move through. What has to be approved, and by whom.]

First tell me what is in my model today — entities, roles, reports, help text, and the checker's verdict on it as it stands — so I can see you have the real file. Then apply only the change I asked for.

Deliver exactly one file I can download: the whole enhanced model, under the name it arrived with. Not a patch, not a diff, not only the new parts, and nothing abbreviated — every line of the file, so I can upload it without merging anything by hand. It must open on a %% line with %%meta name: before the first diagram, and every line in it must be Mermaid or an EML %% directive.

Keep everything I did not ask you to change: every entity, every column, every %%rbac line, every %%report and all the help text. Then show me the before-and-after counts side by side, and tell me plainly if any of them went down.

Then, in your reply text: what changed, the checker result with its counts for my original and for the file you are delivering, and anything you assumed. If the checker cannot be reached from where you are running, say which host failed and how, deliver the model anyway, and keep going — never invent counts, and never hold a phase open waiting for a network call.

Attach your .mmd to the same message. If your model lives in a chat rather than a file, paste it in a single fenced block — the protocol accepts either, and takes the block’s contents as the file.

Changing something people already depend on? Walk it, one change at a time

The prompt above is right for a change you can state in a sentence. It is the wrong trade when the model is large, or old, or generating an application somebody is using — because then the risk is not that the change is wrong, it is that something else moved with it. For that there is llmdetailedenhancement.txt: the same language, the same diagnostics, the same checker, and an interactive enhancement protocol in its section 10.

What section 10 does differently

Section 1 of llmtextenhancement.txt is the batch enhancement: read the file, apply the change, validate, hand it back. Section 10 of llmdetailedenhancement.txt is the interactive one — seven phases separated by approval gates, with your original kept untouched beside the working copy the whole way.

  • Phase 1 — load your model and inventory it, and show you what it contains
  • Phase 2 — agree the change roster before a byte is edited
  • Phase 3 — baseline a working copy; your original is never written to
  • Phase 4 — walk the changes one at a time, checking and counting after each
  • Phase 5 — the cross-cutting pass: what should have moved with the change and did not
  • Phase 6 — validate to clean, and prove nothing was lost
  • Phase 7 — deliver

It costs a conversation instead of a reply. What you get for it is that no change to your model happened without your seeing it first, and that the thing you already had is still there afterwards — checked at every step, not hoped for at the end.

Which of the four do I want?

They divide on two questions: are you starting from a description or from a file, and do you want one answer or a conversation.

Start from a descriptionStart from a .mmd you have
One pass llms-full.txt §1 llmtextenhancement.txt §1
Phased, with approval gates llmdetailed.txt §10 llmdetailedenhancement.txt §10

All four describe the same language and are held to the same published checker. The enhancement pair carries the identical language reference to the pair above it — only the protocol section differs, which is why a model that has read one of them already knows EML.

What comes back, and how to read it

The file is Mermaid — the diagram language — with a small set of %% directives that Mermaid treats as comments and our generator treats as meaning. You can read it, and a Mermaid viewer can draw it.

%%meta name: Field Service
%%meta kind: erd

%%enum JobStatus: scheduled, dispatched, on_site, complete, cancelled

erDiagram
    Customer {
        string id PK
        string name
        email  email UK
        phone  phone OPTIONAL
    }
    Engineer {
        string id PK
        string first_name
        string last_name
    }
    Job {
        string   id PK
        string   customer_id FK
        string   engineer_id FK
        string   status
        datetime scheduled_for
        money    quoted_total
    }
    Customer ||--o{ Job : "raises"
    Engineer ||--o{ Job : "works"

%%entity Job help: A visit an engineer makes to a customer site.
%%field Job.status enum: JobStatus
%%field Job.quoted_total help: What the customer was quoted, before parts used on site.
%%rbac role:dispatcher on Job.update

Every line does one job

  • %%meta name: — names the model. The file opens with it.
  • erDiagram — your entities and their columns.
  • PK FK UK OPTIONAL — the four modifiers that matter.
  • %%enum + %%field … enum: — a closed vocabulary, bound to a column.
  • %%entity … help: and %%field … help: — the help a user reads on screen, and the whole of the manual the generator writes.
  • %%rbac — who may do what.
  • stateDiagram-v2 — the lifecycle a record moves through.
  • flowchart + %%action — a business rule that decides something.

Four things worth checking yourself

The generated application reads a live Application Dictionary — one row per table, column, tab and lookup — and it is derived from this file alone. Four habits decide whether the screens come out usable:

  • Every reference column ends _id and carries FK — that is what makes it a dropdown instead of a box asking for a UUID.
  • Every status column has a %%field … enum: binding — without it the field is free text.
  • Types are specific: email, phone, url, money, date — each one picks its own input control.
  • Entities and non-obvious columns carry help: — it is the only help your users will ever get.

The checker reports all four. Section 3.7 explains why each one matters.

Check the file before you trust it

The same checker the generator runs is published as a module and as a one-command runner. A model that passes here is a model the generator will accept — and a second runner scores whether it is finished, which a clean report does not tell you.

⌨

In a terminal — two lines

curl -sO https://www.appwithai.org/guide/check-model.mjs
node check-model.mjs my-business.mmd

It runs the three passes the protocol asks for, prints the checker's own report, and exits 0 when the file is clean, 1 when the generator would refuse it.

And one more line, for whether it is finished

A clean report says the generator would accept the file. It does not say the model is done — nothing in the checker requires a model to have a lifecycle, a rule, an access rule or a word of help text. One entity with a primary key and a name is a valid model with none of them, and it checks clean.

curl -sO https://www.appwithai.org/guide/audit-model.mjs
node audit-model.mjs my-business.mmd

Twenty-two checks against the delivery checklist — the FK modifier on every reference, an enum behind every status, a state machine with a beginning and an end, help that says something rather than restating a column's own name.
