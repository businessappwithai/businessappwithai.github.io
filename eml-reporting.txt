### 7.1 The reporting application — what Enterprise Reporting makes of the same model

One model generates two applications. The first is everything above. The
second is **Enterprise Reporting** (`businessappwithai/enterprise_reporting_tanstack`)
— a multi-datasource analytics platform with its own server, its own database,
its own users and its own sign-in — loaded with a **reporting pack** derived from
the same `.mmd`: saved queries over the application's `bus_` tables, report and
chart definitions over those queries, an overview dashboard, and one reporting
role per `%%rbac` role. Nothing in the pack is written by hand and nothing in it
is invented. `buildReportingPack`, in the generator (`businessappwithai/app-with-ai-tanstack`,
`packages/generator/src/reporting/pack.ts`), is the single derivation, and every surface that serves reports reads its output —
three derivations would be three answers to "what reports does this model have".

**Three surfaces, one pack.**

| Surface | What runs | Where a reader finds it |
|---|---|---|
| The orchestrator — `./start.sh` in `businessappwithai/app-and-report-with-ai-tanstack` | The real platform, built from its own source, beside the deployed application, both behind nginx | `/app` and `/report` on one origin; `/` lists both sets of accounts |
| The deployable archive — the NestJS stack's `reporting/` directory | The real platform as the `report` service in the archive's own `docker-compose.yml`, cloned at `REPORT_REF` and seeded once by `report-seeder` from `reporting/reporting-pack.json` | Port 3100, beside the application's front end |
| The browser application — chapter 09, or `--standalone` | A **preview** drawn in the platform's own layout and colour tokens, over the same pack carried in `model.json`, labelled as a preview on every screen. Its Administration — users, roles, per-role table grants, the data source, an activity log — is real and enforced on the next query; the SQL editor, NL query, jobs and the report generator need the platform's servers and each says where the real one is | `#/report`, linked from the sign-in screen and from the dashboard |

On the CRM model the browser build and the archive carry the same pack byte for
byte — 133 queries, 116 reports, 84 charts, a ten-widget dashboard, nine roles —
because neither derives its own.

**What the model decides.** Every item in the pack comes from something the
model declares, and a model that declares less gets a smaller pack:

| The model declares | The pack gets |
|---|---|
| An entity | A **register** — its display column, up to two enum columns and two numeric columns, newest first |
| An `%%enum`-bound column | A **breakdown** — rows per value, drawn as a pie at six values or fewer and a bar above that. Two per entity at most: `status`/`state` first, then stage, phase or priority, then type, tier, category or kind |
| `created_at` — every generated table | **Volume per month** over two years, as a line |
| A `kind: state` workflow over a `status` or `state` column | A **lifecycle** over the states the diagram declares, in the diagram's order, zeroes included |
| `integer` and `decimal` columns | **Measures** — totals and averages, grouped by the entity's primary enum column |
| A `oneToMany` relationship | **Children per parent**, ranked |
| A `%%report` | The author's own question, listed first and placed at the top of the dashboard |
| `%%rbac … .read` | One reporting role per declared role, reading exactly the tables those lines admit |
| `%%entity … help:` and `%%field … help:` | The name and description of every report, chart and query |

The overview dashboard takes up to four authored charts, then one tile for each
of the six most central entities — most referenced, carrying a lifecycle,
carrying measures — showing the lifecycle where there is one, else the primary
breakdown, else the volume line.

**So every gap in a model shows up in its reporting layer first.**

- **No help text means reports named after tables** — "bus_account by status"
  rather than "Accounts by status" over a sentence saying what an account is in
  this business. It still runs; nobody wants to read it.
- **A closed vocabulary left as free text is a missing chart.** Only a column
  bound with `%%field … enum:` earns a breakdown — the same binding the
  Application Dictionary needs to draw a select (§3.7).
- **A reference without the `FK` modifier joins as `uuid = varchar`**, so the
  children-per-parent report has to cast the parent's key to text to run at all.
  Mark it `FK` and end its name `_id` or `_by` and the join is typed.
- **A state machine over a column not called `status` or `state` earns no
  lifecycle report.**
- **The platform keys reports by name.** An authored `%%report` whose title
  matches a derived one replaces it — that is the precedence, on purpose — and
  two items of one kind sharing a name fail generation outright rather than
  silently overwrite each other.
- **Write `%%report` for what structure cannot answer** — the overdue, the
  unassigned, the ten largest. The derived baseline describes the shape of the
  data; only the author knows the business running on it.

**Two applications, two sign-ins, and they are not merged.**

| | The generated application | The reporting platform |
|---|---|---|
| Database | The application's own | Its own (`enterprise_config` when deployed) |
| A role decides | What you may **do** to a record | Which tables your queries may **read** |
| `sales_manager` signs in as | `sales.manager@<app>.example.com` | `sales.manager@<app>.reports.example.com` |

The administrator keeps `admin@admin.com` on both sides — the same address, two
different accounts in two different user tables. Each sign-in screen states its
own seeded password, and they differ. Nothing is federated and neither password
works on the other side. **Only `read` rules narrow a reporting role**: nobody
writes through the reporting platform, so a create, update or delete
restriction has nothing to restrict there — and an entity no role may read is
an entity no reporting role can see either.

**What is verified, and what is not.** The checker holds a `%%report` to its
shape (`EML290`–`EML296`) and cannot know whether a column it names exists.
`check-reporting-pack.ts` in the orchestrator is what runs every derived and
authored query against a schema the generator actually emitted, so a renamed
column fails CI rather than every report at run time.

### 7.2 Reporting coverage — mandatory, and it is the whole domain

The derived baseline in §7.1 describes the *shape* of the data. It does not
count here. Only `%%report` lines the author writes count toward the minimums
below, because only the author knows what the business asks.

**7.2.1 The minimum, per role.** Every role declared in `%%rbac` — one per
reporting account (§7.1) — gets **at least 50 reports and at least 50 charts**.
A `%%report` with `chart:` yields one report and one chart, so **50 charted
`%%report` lines per role meets both numbers**; reports without a chart are
extra, never a substitute. Fifty is a floor. A role that reads forty tables
should have far more.

**7.2.2 What counts toward a role.**

- The `%%report` must be one that role **can run**: every `bus_` table its SQL
  names is on that role's read list (`%%rbac role:<role> on <Entity>.read`, or an
  entity with no `read` line at all, which is open to every role). A report a role
  would be refused is not that role's report.
- It must be a **distinct business question**: it differs from the role's other
  reports in the measure, the grouping, the population it filters, or the time
  window — and a person would act on its answer. The same query with another
  `LIMIT`, `ORDER BY` or column order is one report, not two. Never pad.
- It has a plain-language `title:` that reads as the question, and a `help:`
  saying who asks it and what they do with the answer.
- The generated `administrator` and `user` accounts are not declared roles and
  need no set of their own — they run everything the declared roles do. A model
  that *does* declare `administrator` in `%%rbac` owes it its own 50: give it
  the cross-domain, executive and exception questions.
- A report several roles can run counts for each of them, but a role's 50 are
  not met by borrowing another role's: write the questions this role asks.

**7.2.3 Cover the domain, not one corner of it.** Walk every entity the role may
read and write at least one question about it; then keep adding from these
families until the role has 50 distinct ones. A role whose reports are all
"count of X by status" has not covered its domain.

| Family | The question it answers |
|---|---|
| Volume and trend | How many, per month and per quarter; this period against the last |
| Lifecycle | How many sit in each state; how long do they stay; where do they stall |
| Exceptions | What is overdue, unassigned, blocked, expiring, or missing a required fact |
| Rankings | The ten largest, the slowest, the most frequent, by owner, customer or site |
| Money and quantity | Totals, averages, variance, ageing, margin — each over its own measure |
| Conversion and flow | What share moves from one state to the next; throughput per period |
| Relationships | Children per parent, parents with none, value rolled up from child records |
| Quality and compliance | Duplicates, gaps, out-of-policy values, items awaiting approval |
| Ownership and workload | Per person, per team, per queue; who is overloaded or idle |

A role with a short read list may have to lean on these families harder, but if
its tables genuinely cannot support 50 distinct questions, that is a modelling
finding, not a reason to pad: at Gate B widen the role's `read` lines or merge it
with a neighbouring role, and say which you did.

**7.2.4 How to write them so they can be counted.**

- Name each new report with the role as a prefix, lower-case and hyphenated —
  `%%report sales-manager-open-pipeline-by-stage …` — so a role's set can be
  counted by name. The name is the key a report is stored under (`EML292`), so
  it must be unique across the whole file.
- Every charted report names both axes, and both must be columns in its
  `SELECT` list (alias them): `chart: bar x: stage y: total`. Use `line` or
  `area` for time, `pie` only up to six slices, `bar` otherwise.
- Every report keeps the rules of §7.1 and the `%%report` entry in the syntax
  chunk: it only reads, it filters `deleted_at IS NULL`, it joins on the keys
  directly, and it is one line with `sql:` last.
- **ENHANCE:** reports already in the file keep their names and count toward a
  role when the role can run them. Add what is missing to reach 50 per role;
  never rename, merge or drop an existing `%%report`.

Count a role's set from the delivered bytes — never from memory:

```
grep -c '^[[:space:]]*%%report <role-slug>-' <file>.mmd
grep '^[[:space:]]*%%report <role-slug>-' <file>.mmd | grep -c ' chart: '
```

**7.2.5 Report the coverage.** The delivery states, for each declared role, its
charted `%%report` count and its uncharted count, as printed by the commands
above (or, for an ENHANCE file's older reports, counted by reading their SQL and
saying so). A role below 50 is a failed delivery, not a note. The checker and
the audit do not count reports yet — they hold each `%%report` to its shape
(`EML290`–`EML296`) and nothing else — so this count is yours to make and to
state honestly. Never write a number a count did not produce.
