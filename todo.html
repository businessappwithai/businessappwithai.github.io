Todo

The home page says this is early software and not fully tested. This page says what that actually means — five things to finish before the version number reads 1.0.0, and the one that comes after it. There are no dates against any of them, because a date nobody is held to is worse than none.

What 1.0.0 means here

The repository reads 5.1.1 today. That number was never earned — it counted releases, not readiness, and a reader has no way to tell those apart. So the release that is genuinely production grade is 1.0.0, counting from zero, and the five items below are what it is waiting on. Each is written with what done looks like, so that finishing is something anyone can check rather than something we get to declare.

Before 1.0.0

In the order they are being worked on, which is not the same as the order they matter.

1 · In progress

Run the whole generator on the DeepSeek harness — and make it pleasant to use

Two halves of one job. The generator already talks to an OpenAI-compatible endpoint, and the multi-agent pipeline — domain analysis, entities, relationships, the ERD, the human-in-the-loop review — is stack-agnostic by design. The work is running the complete pipeline on the DeepSeek harness and keeping it there: not a model swap in a config file, but every agent, the retrieval that feeds them and the generation that follows, exercised end to end on that harness and kept green.

The second half is usability, and it is the half users actually feel. Today the distance between “describe your business” and “click around the application” is longer than it needs to be: steps that could be inferred are asked for, errors report what failed rather than what to do about it, and the model a run produces sometimes needs hand-editing before the checker will take it.

Done when

A plain-English business description entered into the tool produces a model the checker passes with zero errors and an application that runs, on the DeepSeek harness, with no hand-editing anywhere in between — and the same run works from the hosted page as it does from the CLI.

2 · Planned

Complete documentation for the generator application itself

There is a lot of documentation here, and it is all about something else. The twelve-chapter guide builds a CRM. The specification is the modelling language, written for language models. What is missing is the product: installing it, the project wizard and what each step expects, the rule and workflow editors, what generation actually emits, the enhance and deploy steps, and how to take a generated application and keep working on it.

It also has to cover the parts that surprise people — that two stacks come out of one model, that the browser one has no per-entity source to edit, that a generated application carries its own manual, its own tests and its own migrations.

Done when

Somebody who has never seen this project can go from a clone to a deployed application they have modified, using the documentation alone, without opening the source to find out what a screen does.

3 · Planned

End-to-end testing, over the whole of it

Continuous integration is real here and not decorative: every commit generates an application from a model, builds its backend and front end, migrates a database, starts the server and runs a generated suite against it — twice, once on a WebAssembly Postgres with no database server anywhere. That is a good foundation and it is not complete coverage.

What is not covered yet: the modelling tool's own screens end to end, regeneration over an application somebody has already edited, and the paths a green build can still hide. The project's own notes record a migration that no scaffold entry renders, whose seed fails while the run reports success — exactly the class of defect this item exists to make impossible.

Done when

Every user-facing path has a test that fails when that path breaks, no suite tolerates a failing step by logging past it, and a green build is evidence rather than a habit.

4 · Planned

Audit every license in the product against Apache 2.0

AppWithAI is released under the Apache License 2.0, and it has two dependency trees rather than one: the tools we ship, and the dependencies that end up inside an application it generates for somebody else. The second is the one that matters most, because a generated application is the user's to own, sell and relicense — and a copyleft dependency that travelled there in a template would quietly take that away from them.

The audit has to answer, for every component in both trees:

  • What license it is actually under, read from the package rather than assumed.
  • Whether it is a build-time tool or shipped at runtime — the obligations differ.
  • Whether it is compatible with Apache 2.0 in that role, and whether any of it is copyleft.
  • Whether it reaches a generated application, and under what terms the user then holds it.
  • What attribution we owe, and are not currently giving.
Done when

A checked-in inventory of every dependency and its license across both trees, a NOTICE file that discharges the attribution we owe, a written finding on every incompatibility with what was done about it, and a continuous-integration check that fails when a new dependency arrives under a license nobody has cleared.

5 · Planned

Address the security issues — in what we ship, and in what it generates

This site advertises role-based access control, field-level and row-level security and audit trails as things a generated application gets out of the box. A claim like that is a promise about someone else's data, and it has to be true by demonstration rather than by architecture diagram. Same two trees as the license audit, and the second one matters more for the same reason: a weakness we ship is ours, but a weakness in what we generate is deployed by somebody who trusted the generator.

What has to be gone through, at minimum:

  • Enforcement that fails open. The project's own notes record one already: the table behind state-machine topology is never created, so the guard reads zero rows and every transition is allowed — while continuous integration stays green over it. Every guard needs a test that a permitted action is allowed and a forbidden one is refused, because only the second one catches this.
  • Defaults that must not survive a deployment. A generated application ships with a seeded administrator and a demo password. That is right for a page you click around in and wrong the moment somebody puts it on the internet, and the generator should be the thing that knows the difference.
  • Secrets and configuration. Session and encryption keys, what a generated .env.example implies is safe, and what ends up in a log, a process listing or a committed file.
  • The usual surface, checked rather than assumed. Authentication and session handling, authorization on every route that touches a project, injection through model-supplied identifiers, rate limiting, and dependency vulnerabilities — which the license audit above is already walking the same tree for.
Done when

Every access rule the product advertises has a test that a forbidden action is refused, a generated application cannot be deployed with a demo credential still working, dependency scanning runs on both trees in continuous integration, and the findings — including the ones still open — are written down where a reader can see them rather than summarised as “enterprise security”.

After 1.0.0

Deliberately after. It is the most interesting item on this page and the least urgent, and shipping it before the five above would be building on sand.

6 · After 1.0.0

A complete research agent, running entirely on a local model

Today the Try It Yourself path asks you to leave. You copy a prompt, take it to ChatGPT or Gemini Deep Research, have that model read the specification and write a model file, and bring the file back here. It works — and it means the most valuable step in the whole product happens somewhere we do not control, on a service you pay for, with your business description sent to it.

The item is to close that loop: a research agent in the product itself, doing what those tools do — plan an investigation, search, read, follow what it finds, weigh sources, revise, and cite — but aimed at one deliverable, which is a model of your business that the checker accepts.

All of it on a local model. The default is already Qwen3.8-27B-4bit on an endpoint you run; the work is making it enough — planning, tool use, long-context reading and revision on a 27B model, not on a frontier API with a local fallback. That constraint is the point rather than a limitation to work around: a business describing itself in detail is exactly the kind of thing that should not have to leave the building to become software.

Done when

“Build me an application for X”, typed into the product, produces a researched model with its sources cited and a running application — with no external API call, on hardware a small company owns, and with the human-in-the-loop review still in front of code generation where it belongs.

How this list is kept

This page is versioned with the site, so its history is the change log: what moved, when, and in which commit. Items are not marked done here until the “done when” beside them is true — that is the whole point of writing them that way.

The work happens in the open. If one of these matters to you, or you think the order is wrong, say so on GitHub — and items four and five in particular are ones an outside reader is well placed to find holes in.
